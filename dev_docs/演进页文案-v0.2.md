## 0. 文案纪律（写之前先读）

1. **只写发生过的事**：每个数字、每个版本号都能在 `CHANGELOG.md` 找到原句。
2. **每个节点必须写代价**：没有"放弃了什么"的节点，读起来就是宣传。
3. **不写情绪，写规则**：重点不是"很痛苦"，而是"因此多了哪条门禁"。
4. **不用竞品做参照**：只说我们自己的状态变化。
5. **人称**：起源段用「我」，从 N2 开始切「我们 / 这个项目」。
6. **状态词统一**：已实现 / 打磨中 / 待外部审计 / 建设中 / 实验性。

## 3. M2 · 起源

### 中文（约 450 字）

> 2026 年 5 月 25 日，Liri 的第一个版本是 v0.1：100 次实质提交，一个能跑起来的终端 AI 助手。
>
> 最初想解决的问题很具体：让大模型真的坐在终端里——读文件、跑命令、改代码，而不是只在一个网页输入框里聊天。选择本地模型优先，是因为不想把私人文件传到别人的服务器；选择「安全内生」，是因为它拿到的是一台真实的机器，而不只是一个 API。
>
> 接下来的三个月，能力被一条条铺开：工具、27 个消息渠道、桌面端、语音、知识库。到 8 月，仓库里有 4000 多个文件。
>
> 也是在那时，问题第一次被明确指出来。2026 年 6 月 18 日的代码复查里：`LocalHTTPService` 7200 行，`ChatManager` 3263 行，测试文件 150 个，源码文件 3742 个。两个月后，架构健康度第一次打分：**10/40，D**，105 个超限文件全部未登记。
>
> 那时才明白：判断一个项目能不能被别人接手，不看它有多少功能，而看它踩过坑之后长出了什么规则。
>
> 这页记录的就是这些规则怎么长出来的。

### English (~320 words)

> On 25 May 2026, Liri's first release was v0.1: 100 commits and a terminal AI assistant that could actually run.
>
> The problem was concrete — let the model sit in the terminal, read files, run commands and edit code, instead of chatting in a web input box. Local models first, because private files should not have to leave the machine. Security by design, because the assistant is handed a real computer, not just an API.
>
> Over the next three months, capability was added layer by layer: tools, 27 messaging channels, a desktop client, voice, a knowledge base. By August the repository held more than 4,000 files.
>
> That is also when the problem was named out loud. In the 18 June 2026 code review: `LocalHTTPService` at 7,200 lines, `ChatManager` at 3,263, 150 test files against 3,742 source files. Two months later the first architecture health score came back: **10/40, grade D**, with 105 oversized files, none of them registered.
>
> The lesson: whether a project can be handed to someone else is not decided by how many features it has, but by the rules it grows after it hits a wall.
>
> This page is the record of how those rules grew.

## 4. M3 · 五个转折点

### N1 · 先把能力铺开，边界放后面（2026-05-25 → 2026-08）

- **那时的处境**：v0.1 只有 100 次提交，能跑起来就算赢；功能优先级高于结构。
- **结果**：4000+ 文件、82 个工具、27 个渠道、425 个桌面组件。
- **代价**：审计第一次给出数字时很难看——`LocalHTTPService` 7200 行、`ChatManager` 3263 行；测试/源码比约 4%；首次架构健康度 **10/40（D）**，105 个超限文件全部没登记。
- **证据**：`CHANGELOG.md` v0.1 段；`codebase-review-20260618.md`；`architecture-health-history.json` 首条快照。
- **现在可以参与**：无（历史节点）。

**English**
- **Situation**: v0.1 had 100 commits; shipping beat structure.
- **Result**: 4,000+ files, 82 tools, 27 channels, 425 desktop components.
- **Cost**: the first audit was ugly — `LocalHTTPService` at 7,200 lines, `ChatManager` at 3,263, a 4% test-to-source ratio, and a first health score of **10/40 (D)** with 105 unregistered oversized files.
- **Evidence**: CHANGELOG v0.1 · `codebase-review-20260618.md` · first snapshot in `architecture-health-history.json`.

---

### N2 · 先学会量自己（2026-08-09 → 2026-09-30）

- **那时的处境**：问题人人能感觉到，但没人说得清"差多少"。
- **决策**：把架构质量做成可重复的评分与台账（`scripts/architecture-health.ts`），超限文件必须登记；**放弃**了"靠自觉保持整洁"这个假设。
- **结果**：9 次快照；未登记超限文件 105 → 0（后回弹到 2）；超限清单从"没人知道"变成一份可追溯的台账。
- **代价**：**登记不等于拆分**——`ChatManager` 反而从 3263 行涨到 7036 行；评分口径本身也在变（D、C 之间来回），所以它只能当体检表，不能当 KPI。
- **证据**：`scripts/architecture-health.ts`；`dev_docs/architecture-health.json`；首尾两次快照。
- **现在可以参与**：认领一个超限文件的拆分（见 M6）。

**English**
- **Situation**: everyone could feel the problem, nobody could say how bad it was.
- **Decision**: make architecture quality a repeatable score with a register (`scripts/architecture-health.ts`), and **give up** the assumption that cleanliness survives on discipline alone.
- **Result**: nine snapshots; unregistered oversized files went from 105 to 0 (later back to 2); the list became a traceable register.
- **Cost**: **registering is not splitting** — `ChatManager` grew from 3,263 to 7,036 lines; the scoring itself kept changing, so it is a health check, not a KPI.
- **Evidence**: `scripts/architecture-health.ts` · `dev_docs/architecture-health.json`.

---

### N3 · 一次删错，换来一条删除流程（2026-10-08 → 10-09，v0.4.69 → v0.4.72）

- **触发**：v0.4.69 的"死面清理"把沙箱与隔离子系统当成死代码删掉——那一版动了 170 个文件，+9340 / −10174 行。
- **决策**：第二天 v0.4.71 整批回滚：恢复 24 个文件（`IsolationManager`、`EnhancedSandboxManager`、`PTYSandbox`、`SSHSandbox`、`docker/**`、`WorkspaceManager`、`ProcessRegistry`、`ResourceLimitManager` 等，外加 5 项测试），并回滚 21 个存活文件的配套改动。
- **结果**：v0.4.72 落地删除流程 `code-deletion.md`（CD01–CD07）：**先取证、再摘入口、后删实现**。"看起来没人用"不再是删除理由。
- **代价**：删一个文件要先写证据，清理变慢；但比删错再回滚快。
- **证据**：`CHANGELOG.md` v0.4.69 / v0.4.71 / v0.4.72 三段。
- **现在可以参与**：按 CD01–CD07 做一次"死代码候选"核对（good first issue）。

**English**
- **Trigger**: the v0.4.69 "dead code cleanup" treated the sandbox and isolation subsystem as dead: 170 files touched, +9,340 / −10,174 lines.
- **Decision**: the next day, v0.4.71 rolled the whole thing back — 24 files restored (`IsolationManager`, `EnhancedSandboxManager`, `PTYSandbox`, `SSHSandbox`, `docker/**`, `WorkspaceManager`, `ProcessRegistry`, `ResourceLimitManager` and more, plus 5 test suites) and 21 live files reverted to match.
- **Result**: v0.4.72 turned deletion into a process, `code-deletion.md` (CD01–CD07): **collect evidence, detach entry points, then delete**. "Nobody seems to use it" stopped being a reason.
- **Cost**: deleting now takes longer — you write evidence first. Still cheaper than a rollback.
- **Evidence**: CHANGELOG v0.4.69 / v0.4.71 / v0.4.72.

---

### N4 · 把规则变成门禁（2026-10-10 → 10-22，v0.4.76 → v0.5.4）

- **那时的处境**：规则写在文档里，靠自觉；文档和代码开始漂移。
- **决策**：每条规则都做成 CI 阻断，而不是建议——v0.4.76 五道门禁 + `doc-gate` + `sandbox-negative` 必需 job；v0.5.0 硬编码基线 413 键；v0.5.3 状态词表 34 个值 / 1795 对基线（只拦增量）；v0.5.4 启动面、关键模块、内核面三道。
- **结果**：`lint:arch` 违规 0；测试从 3029（09-21）涨到 7488（10-20）。
- **代价**：每次提交多几秒；改词表要同步基线——**口径不能再随手改**，这恰恰是目的。
- **证据**：`AGENTS.md` 门禁清单；`.github/workflows/ci.yml`；CHANGELOG v0.4.76 / v0.5.0 / v0.5.3 / v0.5.4。

**English**
- **Situation**: rules lived in documents and relied on discipline; documents and code began to drift.
- **Decision**: turn each rule into a CI blocker — v0.4.76 added five gates plus `doc-gate` and a required `sandbox-negative` job; v0.5.0 froze 413 hardcoding baseline keys; v0.5.3 introduced `lint:state-ratchet` (34 vocabulary values, 1,795 baseline pairs, delta-only); v0.5.4 added startup-surface, critical-module and kernel-surface gates.
- **Result**: `lint:arch` violations at 0; tests grew from 3,029 (21 Sep) to 7,488 (20 Oct).
- **Cost**: a few seconds per commit, and baselines must be regenerated with every vocabulary change — the point is that the definitions can no longer drift silently.
- **Evidence**: `AGENTS.md` · `.github/workflows/ci.yml` · CHANGELOG v0.4.76 / v0.5.0 / v0.5.3 / v0.5.4.

---

### N5 · 内核收缩：从 5336 行到独立包（2026-10-05 → 10-28，v0.4.60 → v0.5.22）

- **那时的处境**：core 既是入口实现，又是所有能力的公共腹地，谁都能往里加。
- **决策**：三步走——先砍（`CoreAPIImpl` 5336 → 2521 行），再抽包（v0.5.10 `@openliri/kernel` 独立，core 146 → 113 个文件，K01–K08 内核门禁），最后外移（v0.5.22：37 个不满足"零 I/O / 零上层依赖"的模块下沉 `app/src`，同步 470+ 处 import，5 类基线重生成）。
- **结果**：内核对外只剩一层薄接口，外部贡献第一次有了明确边界。
- **代价**：一次大迁移，全部基线重生成；10-18 起改成按批次收口，提交密度主动降下来。
- **证据**：`CHANGELOG.md` v0.4.60 / v0.5.10 / v0.5.22；commit `e59929448`。
- **现在可以参与**：内核边界之外的新能力（模块从 `app/src` 起步，不必进内核）。

**English**
- **Situation**: the core was both the entry implementation and everyone's shared backyard — anyone could add to it.
- **Decision**: three steps — shrink (`CoreAPIImpl` 5,336 → 2,521 lines), extract (v0.5.10 shipped `@openliri/kernel`; core went from 146 to 113 files with kernel gates K01–K08), then evict (v0.5.22 pushed 37 modules that failed the "zero I/O / zero upward dependency" rule down into `app/src`, updating 470+ imports and regenerating five baseline families).
- **Result**: the kernel now exposes a thin interface; external contributions finally have a boundary.
- **Cost**: one large migration plus full baseline regeneration; since 18 Oct, work lands in batches and commit density is deliberately lower.
- **Evidence**: CHANGELOG v0.4.60 / v0.5.10 / v0.5.22 · commit `e59929448`.

## 6. M6 · 参与方式（三张卡 + 审计清单）

### 中文

1. **认领一块空白** — Domain-first 知识域隔离已有设计稿（`domain-first-plan.md`），Phase A/B/C 未实施；内核边界之外的功能也不需要先进内核。
2. **帮我们把账还掉** — 121 个超限文件待拆，最大的是 `ChatManager`（7036 行）；测试覆盖率门槛还没建。
3. **审计我们的安全** — 五层防线与 6 种沙箱后端已实现，规则源码可查，但**还没有第三方审计**。这是我们最想要的反馈。

**安全审计清单（照着就能做）**

- [ ] **危险命令规则**：37 条规则在哪、怎么触发——试着构造一次，看拦截是否落在预期的那一条
- [ ] **提示注入规则**：14 条注入规则，喂一段恶意文档看是否被拦
- [ ] **Shell 规则**：10 条 shell 白/黑名单，验证绕过路径（管道、子 shell、编码）
- [ ] **沙箱降级逻辑**：6 种后端各自在什么条件下降级、降级后是否 fail-closed
- [ ] **审批四段**：`requested → presented → decided → recorded` 是否有漏段或乱序
- [ ] **越权面**：工具调用能否绕过权限分类器直接落盘 / 执行

> 入口：`app/src/security`、`app/src/sandbox`、`app/src/permission`（目录链接见自查表"源码"列）。
> 发现问题的直接开 Issue，标签 `security`。

按钮：`在 Issues 里认领 / 提问 →` ｜ `打开安全自查路径 →`

### English

1. **Claim a blank** — Domain-first knowledge isolation has a design (`domain-first-plan.md`) but Phases A/B/C are unimplemented; new capabilities do not need to enter the kernel.
2. **Help us pay down the debt** — 121 oversized files are waiting to be split, the largest being `ChatManager` at 7,036 lines; there is no coverage gate yet.
3. **Audit our security** — five defense layers and six sandbox backends are implemented and their rules are readable in source, but **no third-party audit has been done**. This is the feedback we want most.

**Security audit checklist (you can just follow it)**

- [ ] **Dangerous-command rules**: 37 rules — where they live, how they fire; build one case and check it is blocked by the expected rule
- [ ] **Prompt-injection rules**: 14 rules — feed a malicious document and see whether it is stopped
- [ ] **Shell rules**: 10 allow/deny entries — try bypass paths (pipes, subshells, encoding)
- [ ] **Sandbox degradation**: the conditions under which each of the 6 backends degrades, and whether it fails closed
- [ ] **Approval stages**: `requested → presented → decided → recorded` — look for missing or out-of-order stages
- [ ] **Privilege surface**: can a tool call bypass the permission classifier and write or execute directly?

> Entry points: `app/src/security`, `app/src/sandbox`, `app/src/permission` (also linked from the self-check table's Source column). Open an issue with the `security` label.

Button: `Claim or ask in Issues →` | `Open the security path →`
