## 0. 结论先行

把官网从「功能清单 + 快速迭代期免责声明」，改成**「演进叙事 + 可验证证据 + 明确邀请」**。

三件事，按影响排序：

1. **新增独立「演进 / Build Log」页**：5 个转折点，每个节点 = 问题 → 决策 → 代价 → 架构结果 → 证据链接 → 参与入口。这是本次最大的内容投入。页面保持纯叙事（M1–M6），不放技术清单。
2. **新增 `/status` 页 + 首页从 21 个区块收敛到 14 个左右**：自查表、架构健康度、限制清单、版本节奏这四类「项目健康度」内容集中到 `/status`；首页只留结论 + 一个 200 字引子 + 精简版限制。
3. **把「快速迭代期」从免责声明改成邀请理由**：每个未完成项都对应一个可认领的入口。

一句话主轴：**把一个人写出来的 4000 个文件，收敛成有边界、有门禁、能被别人接手的系统。**

## 2. 叙事设计

### 2.1 目标读者

| 读者 | 关心什么 | 对应内容 |
|---|---|---|
| 潜在贡献者（首要） | 这个项目值不值得投入时间、我能插哪只手 | 演进页 + 空白架构图 + 认领入口 |
| 技术选型者 | 能不能信、边界清不清楚、坏了怎么办 | 门禁规则、误删后的恢复机制、已知限制 |
| 围观者 | 这是个什么东西 | 首页 Hero + About + 能力卡 |

### 2.2 四幕结构

**铺开 → 撞墙 → 收敛 → 邀请**

- 铺开（能力先行，没有边界）
- 撞墙（清理"死面"误删沙箱子系统；架构评分只有 D）
- 收敛（回滚恢复 → 删除流程 CD01–CD07 → 门禁体系 → 内核外移）
- 邀请（当前架构与空白图里标出的 3 块空白 = 正在招人的地方）

### 2.3 声音与人称

- 前两幕可用「我」；从"决策"开始切到「我们 / 这个项目」，让读者站进来。
- 不写情绪，写产出：**「很痛苦」→「因此多了什么规则」**。
- 每个功能描述后尽量补一句**边界或代价**（例如"支持 27 个渠道；部分渠道需要自备凭据与公网回调"）。

### 4.3 五个转折点（已按仓库实读校正，完整文案见配套文件）

> 考据结论先放在前面：**这不是一条"设计好了再实现"的线，而是一条"先跑起来、再被现实打回来、然后长出规则"的线。** 所有节点都能在 `CHANGELOG.md` 对应版本段逐字核对。
>
> **排序说明**：五张卡片**按因果排序，不是日历顺序**。N1「铺开」与 N2「量化」在时间上是交叠的（2026-08 → 10 期间既在铺开也在量化），读者看时间戳时不要当成串行；M5 时间线里会如实呈现重叠。

**N1 · 先把能力铺开（2026-05-25 → 2026-08）**
- 处境：v0.1 首发时是 100 次实质提交；之后优先把能用的东西做出来，边界其次。
- 结果：4000+ 文件、82 工具、27 渠道、425 桌面组件。
- 代价：2026-06-18 代码复查已点出巨石文件（`LocalHTTPService` 7200 行、`ChatManager` 3263 行），测试文件 150 / 源码 3742（约 4%）；2026-08-09 首次健康快照 **10/40（D）**，105 个超限文件全部未登记。
- 证据：`CHANGELOG.md` v0.1 段；`dev_docs/codebase-review-20260618.md`；`dev_docs/architecture-health-history.json`。

**N2 · 先学会量自己（2026-08-09 → 2026-09-30）**
- 决策：把"架构好不好"变成可重复的评分与台账（`scripts/architecture-health.ts`），超限文件必须登记。
- 结果：9 次快照；未登记超限文件 105 → 0（后回弹到 2）；2026-09-30 复测得 13/40，超限 121 个合计 16 万行。
- 代价：**登记 ≠ 拆分**——`ChatManager` 从 3263 行涨到 7036 行；评分口径本身也在变（D/C 之间波动），所以只能当体检表，不能当 KPI。
- 证据：`scripts/architecture-health.ts`、`dev_docs/architecture-health.json`、首尾两次快照。

**N3 · 一次删错，换来删除流程（2026-10-08 → 10-09，v0.4.69 → v0.4.72）**
- 触发：v0.4.69 的"死面清理"把沙箱与隔离子系统当成死代码删除（该版 170 个文件、+9340/−10174）。
- 决策：次日 v0.4.71 整批回滚——恢复 24 个文件（`IsolationManager` / `EnhancedSandboxManager` / `PTYSandbox` / `SSHSandbox` / `docker/**` / `WorkspaceManager` / `ProcessRegistry` / `ResourceLimitManager` 等 + 5 项测试），并回滚 21 个存活文件的配套改动。
- 结果：v0.4.72 落地删除流程规则 `code-deletion.md`（CD01–CD07）：先取证、再摘入口、后删实现；"看起来没人用"不再是删除理由。
- 代价：清理一个文件要先写证据，流程变慢。
- 证据：`CHANGELOG.md` v0.4.69 / v0.4.71 / v0.4.72 段。

**N4 · 把规则变成门禁（2026-10-10 → 10-22，v0.4.76 → v0.5.4）**
- 处境：规则写在文档里，靠自觉，拦不住。

- 结果：`lint:arch` 违规 0；测试 3029（09-21）→ 7488（10-20）。
- 代价：每次提交多几秒；改词表要同步基线，口径不能随手改。
- 证据：`AGENTS.md` 门禁清单、`.github/workflows/ci.yml`、`CHANGELOG.md` v0.4.76 / v0.5.0 / v0.5.3 / v0.5.4。

**N5 · 内核收缩：从 5336 行到独立包（2026-10-05 → 10-28，v0.4.60 → v0.5.22）**

### 4.4 M4 · 当前架构与空白图（**不做未定稿的"目标架构"**）

**为什么改**：评审指出，「目标架构」若在 `domain-first-plan.md`、`Liri_契约层详细设计文档.md`、`第四次架构复查报告.md` 之间拼合，会变成缝合怪。核对后的结论是：这三份文档说的不是同一层东西——

| 文档 | 它实际描述的是 | 能否当目标态的唯一依据 |
|---|---|---|
| `domain-first-plan.md` | 知识域隔离的目标形态（Phase A/B/C） | 只能覆盖知识域一层，且**未实施** |
| `Liri_契约层详细设计文档.md` | 任务台账/哨兵/粒度等协作契约 | 是跨层约束，不是架构分层 |
| `第四次架构复查报告.md` 等 | 当前问题与收敛进度 | 只能当现状依据 |

因此本项目**没有一个已定稿的完整目标架构**。在这种状态下画"目标架构图"，本身就是过度承诺。M4 改为 **gap map（缺口图）**：

- **一张现状图**：`入口（终端/桌面/渠道）→ 内核 → 能力域（工具/技能/工作流）→ 运行时（沙箱/权限/预算）→ 治理（门禁/证据）→ 交付（文档/发布）`，每层标注当前状态（稳定 / 重构中 / 有问题）。
- **叠加 3 块已确认的空白**（只画这三块，不画虚构的目标层）：
  1. **知识域隔离**：`domain-first-plan.md` 已设计，Phase A/B/C 未实施；
  2. **协作契约落地**：契约层设计稿存在，台账 / LoopProfile 是否落地未核实；
  3. **覆盖率门禁**：复查时约 4%，CI 门槛未建。
- **每块空白必须挂真实 Issue**；没有 Issue 的空白不画（否则是空承诺）。
- **图例**：`稳定`（实线）/ `重构中`（虚线）/ `空白`（空心 + "需要人"）；状态同时用描边样式 + 文字标签，不只靠颜色。
- **技术实现**：内联 SVG，不引第三方图表库。
- 「待确认」：如果你能指定一份**已定稿**的目标架构文档，再升级成双层图；在此之前，gap map 是唯一诚实的画法。

### 4.7 参与入口规范（已定：只做 Issues，不做 Discussions）

**三个 issue 模板**（`.github/ISSUE_TEMPLATE/`）：

| 模板 | 字段 | 关键约束 |
|---|---|---|
| `bug.yml` | 环境（OS / 版本 / 安装方式）→ 复现步骤 → 期望 vs 实际 → 日志片段 | 提示先脱敏，密钥不要贴 |
| `feature.yml` | 要解决的问题 → 现在的临时办法 → 是否愿意提 PR | 先问"为什么"，不先问"要什么功能" |
| `audit.yml` | 审计范围（危险命令 / 注入 / shell / 沙箱 / 审批 / 越权）→ 复现方式 → 是否已私密报告 | **不接收漏洞细节**，只接收流程与覆盖范围 |

**两个标签 + 一个专用标签**：`good first issue`、`help wanted`、`security`。

**种子 issue（P1 内建好，≥6 条，每张卡指向具体 issue 而不是 issues 列表页）**

1. 认领 · Domain-first Phase A 拆成可执行子任务
2. 认领 · `ChatManager`（7036 行）拆分第一阶段
3. 认领 · 补 `infrastructure/http/handlers/` 的测试
4. 还债 · 给 CI 加覆盖率门槛（复查时约 4%）
5. 审计 · 危险命令规则（37 条）的复现用例
6. 审计 · 6 种沙箱后端降级逻辑整理成对照表

**安全入口必须写明的两句话**：

> 发现**漏洞细节**请按 `SECURITY.md` 私密报告，不要开公开 issue。
> 公开 issue 只用来讨论审计流程、覆盖范围与复现方法。

**为什么不现在开 Discussions**：首发期大概率无人发帖，空讨论区比没有更减分。等外部 issue 积累到 20+、真的出现"不是 bug 的讨论"再开，那时才有内容撑住。
